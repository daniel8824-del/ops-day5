§ 온톨로지 이해 · 오늘의 핵심 개념

온톨로지 | 데이터의 양이 아니라 관계

한 줄 정의
온톨로지 = entity(개념) + 관계로 짜인 의미 그래프. AI가 "단어"가 아니라 "무엇이 무엇과 어떻게 연결되는지"를 보게 만드는 layer입니다.

1온톨로지가 뭔데? | 비유로 단번에

한마디로 "점(개념) + 선(관계)으로 그린 지식 지도"입니다. 셋 다 같은 얘기입니다:

🏠 가족 관계도
'아빠' 옆에 '엄마(부부)'
'나(자식)' 화살표.
점(사람)+선(관계) = 온톨로지
🚇 지하철 노선도
역=노드, 선로=엣지,
노선도 전체=그래프.
"환승하면 어디까지"가 한눈에
📚 위키 + 사전
위키는 글자만.
온톨로지는 "이 단어=무엇,
무엇과 어떤 관계"까지 명시

스키마 vs 온톨로지 | "떡볶이"로 보면

📋 스키마 (납작한 카드)
떡볶이 · 분식 · 5,000원 · 맵기 중간
→ 속성만. 다른 것과 연결 ❌
🕸 온톨로지 (관계망)
떡볶이 →[필수] 떡  →[매운맛★★★] 고추장
       →[단짝] 순대  →[원조] 신당동
→ 관계 + 강도까지 ✅

스키마는 "떡볶이 가격은 5,000원"까지. 온톨로지는 "무엇으로 만들고, 무엇과 단짝이고, 어디가 원조인지" 관계까지 연결합니다.

"그"의 힘 | 특정화

"수의사"는 그냥 직업입니다. "그 수의사"가 되는 순간 (잘 고치나·빠른가·강아지 전문인가) 까지 정의됩니다. 이 "그"를 붙이는 과정이 온톨로지이고, LLM이 모르는 "우리 회사의 그것"이 바로 가치입니다.

일반"그"가 붙으면 (= 온톨로지)
수의사그 수의사 | 잘·빠르게·강아지 전문인지까지
고양이그 고양이 | 털색·성격·사료·병력·좋아하는 장난감
POS 단말그 단말 | 어느 매장·어떤 SW 스택·인시던트 이력까지

더 많은 비유 (인제스트 = 소 되새김질 · 임베딩 = 의미 좌표 "왕↔여왕 가깝고 왕↔감자 멀다" · Neo4j = 그래프 전용 창고 등)와 인터랙티브 그림: crab-guide 비전공자 가이드 (오픈크랩 제품 소개·가격도 함께 있음).

2핵심 개념 4개 | 비유로

온톨로지 외에 이 4개만 잡으면 대화의 80%가 들립니다.

⬇️ 인제스트 (Ingest) | "삼키고 소화시키기"

🐄 소 되새김질
풀을 그냥 삼키는 게 아니라 다시 잘게
부수고 분해해서 영양분만 흡수.
인제스트도 "먹고 → 분해 → 의미만 추출"
📖 학생 핵심정리노트
책을 통째로 들고 가는 게 아니라
"핵심 정리 노트"만 만들어 들고 감.
원본은 안 남기고 지식 지도만 저장

자료(PDF·이미지·문서·웹)를 넣어 가공·저장. 원본 파일은 안 올라가고 정리된 의미만 저장되어 가볍고 보안에 유리.

🗄 Neo4j | "그래프 전용 창고"

📦 거미줄 전용 창고
엑셀(표)은 일반 창고에 잘 들어감.
"거미줄 같은 관계 그림"을 엑셀에
넣으면 망함 → 그래프 전용 창고가 Neo4j
🚇 환승 0.1초 답
"3번 환승해 갈 수 있는 모든 역"을
0.1초에 답하려면 엑셀로는 불가.
그래프 DB는 이걸 잘함

SQL = 엑셀 표 다루는 전통 방식 / Neo4j = 그래프 전문. 오늘 실습은 Neo4j 없이 로컬 SQLite로 충분 (대규모일 때만 선택).

📐 벡터 임베딩 | "의미 좌표"

🗺 도시 지도
단어를 좌표 위에 흩어놓기.
"왕" ↔ "여왕"은 좌표가 가깝고
"왕" ↔ "감자"는 멀다 (의미 거리)
🎵 향수 지문
향수 = 시트러스8·머스크3·우디5...
숫자 조합이 비슷하면 비슷한 향.
단어도 1536개 숫자로 변환됨
두 문장좌표 거리결과
"왕이 명령을 내렸다" vs "여왕이 결정을 발표했다"0.18 (가까움)같은 의미로 인식 ✅
"왕이 명령을 내렸다" vs "감자를 삶아 으깼다"0.92 (멀음)다른 의미 ❌

키워드 검색은 "왕" 글자가 있어야 찾지만, 임베딩은 "통치자가 지시했다"도 좌표가 가까워 같이 찾아냅니다.

🔍 RAG · 그래프RAG · BM25 | "오픈북 시험"

AI가 머리에서만 짜내면 거짓말(할루시네이션). 그래서 "먼저 자료 찾고 → 보고 답한다"가 RAG. 답 모르면 찍는 학생(일반 AI) vs 책 펴서 답하는 학생(RAG). 책 = 온톨로지 팩.

방식찾는 것비유
BM25"정확히 그 단어" (키워드)구글 단순 검색
벡터 RAG"비슷한 의미" (단어 달라도)"비슷한 노래" 추천
그래프 RAG"이거랑 연결된 거 다" (추론)족보·계보 추적
RAG의 다음 진화 = 그래프 추론. "이 약 먹으면 졸려?" → 일반 RAG는 "졸음" 키워드 문장만(근거 약함). 그래프 RAG는 약 → 성분 → 부작용 → 졸음 체인을 따라가 근거 있는 답. 운영으로 옮기면 "이 결제 모듈 바꾸면 어떤 매장·티켓·담당자까지"가 같은 질문입니다. (셋 다 써야 품질↑, 그래프RAG만 쓰면 느림)
ingest vs extract | 가장 헷갈리는 둘. ingest는 원본을 "검색 색인"으로 저장(그래프 안 생김), extract는 LLM이 읽고 "노드·엣지(그래프)"를 만듭니다. 온톨로지 그래프는 extract에서 나옵니다. 그래서 강사는 extract로 팩을 제작하고(LLM 키 필요), 학생은 그 팩을 ingest(import)로 설치하면 추출 없이 즉시 노드를 받습니다.

3빅데이터 vs 온톨로지 | 반대 방향

"AI 시대엔 빅데이터가 왕"이 통념이지만, LLM 자체가 이미 빅데이터 덩어리(인터넷 글 다 학습). LLM의 한계를 넘으려면 "빅데이터의 반대 = 아주 사적인 데이터"가 필요합니다.

⬅️ 빅데이터 (구시대)
• 엄청 큼 · 일반적 · 평균화
• LLM이 이미 다 학습함
• 추가 가치 한계 도달
➡️ 온톨로지 (새 시대)
• 작음 · 특정 · 맥락화
• "그 수의사" 같은 특정화
• 누구나/팀이 만들 수 있음
암묵지(暗默知)의 자산화 | 사내 업무 매뉴얼·운영 노하우·"우리 팀만 아는 그것"은 LLM이 절대 모르는 핵심 가치입니다. 말로 못 푸는 이 암묵지를 온톨로지로 만들면 팀이 공유하는 지식 자산이 됩니다. 농경=토지, 산업=공장, AI사회=맥락이 담긴 사적 데이터.

49-Space | 모든 데이터는 이 9칸 중 하나

어떤 자료든 넣으면 자동으로 9개 의미 공간 중 하나에 매핑됩니다. 온톨로지를 짜는 골격(문법)입니다.

#공간"무엇"예
1주체 Subject누가 행동하나사람·팀·조직·AI 에이전트
2리소스 Resource무엇을 다루나프로젝트·문서·파일·API
3증거 Evidence무엇을 관찰했나텍스트 조각·로그·원자료
4개념 Concept추상적 무엇키워드·토픽·엔티티
5주장 Claim"X는 Y다" 명제가설·결론·인과
6커뮤니티 Community노드 군집그래프상 자연 군집
7결과 Outcome측정된 성과·리스크KPI·매출·리스크
8레버 Lever움직일 다이얼시뮬레이션 입력 변수
9정책 Policy룰·승인·민감도권한 정책·승인 워크플로

멘탈모델: "들어오면 → 어느 공간? → 어떤 공간과 연결?" 이 두 질문이 끝. 오늘 두 팩(개발/운영)도 다 이 9칸으로 짜였습니다.

5메타엣지 | 화살표 그 이상

일반 그래프
노드 + 엣지(화살표) 끝.
A → B 연결만. 관계 종류·강도 없음
메타엣지 (관계의 5속성)
엣지마다 ① 정의 ② 엣지 간 관계
③ 하이라키(층위) ④ 권한 ⑤ 강도

친구 관계도(점·선)가 아니라 "친한 정도(강도) + 사귄 기간(층위) + 비밀 공유 여부(권한) + 어떻게 친해졌나(정의)"까지 기록한 관계도. 영향 분석(impact)이 가능한 이유입니다.

6원본은 로컬, 의미만 클라우드 | 보안 모델

엔터프라이즈의 핵심 모순: "내 데이터를 AI에 보여줘야 똑똑한 답이 나오는데, 그러면 보안이 깨진다." 온톨로지의 답:

100MB 계약서 / 도면 / 고객 데이터 (민감 원본)
   ↓ 로컬에서 그래프 빌드 (원본은 절대 안 나감)
   ↓ 노드·엣지 = 의미만 추출 (약 1KB · 10만 배 압축)
클라우드 / AI는 "의미"만 받아 답변
→ 원본 픽셀·문장은 한 글자도 외부로 안 나감. 압축 + 보안 둘 다.
규제·보안 강한 환경(의료·법률·금융·리테일)에서 "민감 원본은 안 나가고 + AI 기능은 풀로"를 둘 다 충족. 도시바·아모레 사내 도면·고객·운영 데이터도 같은 원리로 안전하게 AI에 붙입니다.

7왜 지금 온톨로지인가

AI 발전 흐름을 단계로 보면 지금은 에이전트 단계입니다. 팀·조직 규모로 가면 각 에이전트가 같은 도메인을 제각각 이해하는 벽에 부딪힙니다.

규칙 → 머신러닝 → 에이전트 (현재) → 온톨로지 (다음 병목) → AGI

에이전트 다음 단계가 온톨로지입니다. 모든 에이전트가 같은 의미 기반을 공유해야 비로소 협업·오케스트레이션이 됩니다.

OpenCrab은 위 온톨로지를 직접 만들어 보기 위한 실습 도구입니다. 로컬에서 ingest·extract·query·그래프까지 한 번에 됩니다. 오늘은 이 도구로 "온톨로지를 손에 익히는 것"이 목적입니다.

§ 온톨로지 실습 · 오늘의 메인 (시간 대부분)

OpenCrab으로 온톨로지 직접 만들기

실습 목표
강사가 만든 도시바 POS 팩 2개(개발/운영) 중 본인 직무 팩을 설치 → 질의 → 의견 수렴. 그다음 본인 문서로 본인 온톨로지를 extract해 팩으로 보관하고, 그 결과를 스킬·MCP 아이디어로 발전시킵니다.

1강사 시연 | 같은 POS 도메인, 두 팀의 온톨로지

강사가 도시바 POS 관련 원본 문서를 OpenCrab extract로 통째로 넣어 만든 팩 2개를 d3 그래프로 보여드립니다. 같은 도시바 POS인데 팀 관점에 따라 온톨로지가 다릅니다.

개발팀 팩 (무엇으로 만드나)
소스: acli · GitLab CI · Jira/Confluence ·
      ELERA 플랫폼 · TCx Sky OS · TCx 단말 스펙
node: Jira Issue · Pipeline · ELERA POS · TCx Sky ...
edge: depends_on · part_of · contributes_to ...
운영팀 팩 (무엇이 돌아가고 터지나)
소스: 도시바 POS 제품/지원 · 운영 runbook ·
      ITSM 인시던트/티켓 패턴
node: 매장 · 단말 · 인시던트 · 티켓 · 운영자 · KPI
edge: logged_as · describes · degrades ...

두 팩은 OpenCrab extract(LLM이 원본 전문에서 entity·관계 추출)로 생성, apps/web d3 그래프로 시각화. 그래프 DB(Neo4j) 불필요, 로컬 SQLite에 보관.

2학습자 | 본인 직무 팩 설치 + 질의 실습

본인 직무에 맞는 팩(개발자→개발팩, 운영자→운영팩, 둘 다도 가능)을 받아(자료) OpenCrab에 설치하고 자연어로 질의합니다.

개발팩 질의 예
"ELERA POS는 어떤 OS 위에서 돌아가?"
"acli로 work item 만드는 명령은?"
"GitLab 파이프라인은 어떤 단계로 구성되지?"
"이 SW 버전 바꾸면 영향 범위는?" (impact)
운영팩 질의 예
"POS_DOWN이 어떤 KPI에 영향을 주지?"
"강남역점 단말 인시던트 흐름은?"
"P1 티켓 에스컬레이션 정책은?"
"이 인시던트의 영향 매장 사슬은?" (impact)

질의 결과를 함께 보며 "우리 환경이면 무엇을 더 붙일까"를 나눕니다. (질의는 OpenCrab MCP의 ontology_query · ontology_impact가 처리)

3학습자 | 본인 문서로 본인 온톨로지 + 팩 보관

본인 문서를 골라 OpenCrab에 ingest(원본을 벡터로 저장) → extract(LLM이 노드·엣지 생성)로 본인만의 온톨로지를 만들어 팩으로 보관합니다. 정석 순서는 ingest → extract입니다.

자연어 요청 (ingest → extract → query → export)
"내 문서 폴더 [경로]를 OpenCrab에 ingest하고 extract해서 노드·엣지를 만들어줘. 끝나면 '[관심 키워드]'로 query하고, 이 온톨로지를 팩(nodes.jsonl + edges.jsonl)으로 export해줘."

extract는 LLM이 entity를 뽑으므로 키가 필요합니다 (강사가 팩 만들 때와 동일). 본인 CLI 모델 또는 OpenRouter 키를 씁니다. 강사 팩만 쓸 거면 이 단계는 건너뛰어도 됩니다.

✓ 산출물

  • 본인 도메인 온톨로지 (로컬 ./opencrab_data/)
  • 본인 팩 ZIP (manifest + nodes.jsonl + edges.jsonl + sample_queries) | 팀에 그대로 공유 가능

4아이디에이션 | 질의 결과 → 스킬 / MCP tool ★

온톨로지 질의에서 반복적으로 쓰는 패턴이 보이면, 그걸 스킬이나 MCP tool로 굳혀 자동화합니다. Day 4에 설치한 brainstorming 스킬로 발산부터 시작하세요.

자연어 요청
"brainstorming 스킬로 시작. 방금 온톨로지 질의 결과 중
 자동화할 패턴 후보를 같이 추려줘."
질의 패턴 예시굳히면
"결제 실패 → 영향 entity → 담당자 → 티켓"MCP tool impact_to_ticket
"단말 모델 → 호환 SW → 펌웨어 버전"스킬 device-compat-check
"신규 매뉴얼 → 관련 entity 자동 연결"ingest hook (PostToolUse)
여기가 오늘의 핵심입니다. 온톨로지(의미) → 패턴 발견 → 스킬/MCP(자동화). 단순히 검색하는 데서 끝나지 않고, 반복 패턴을 도구로 만들어 팀이 재사용합니다.

5그래프화 (선택 심화)

여유가 있는 분은 본인 온톨로지도 d3 그래프로 띄워봅니다. ① 코드는 OpenCrab apps/web에 이미 있고, ② 본인 데이터로 바꿔 끼우면 됩니다.

자연어 요청
"OpenCrab apps/web 그래프 뷰어를 내 온톨로지 데이터에
 연결해서 localhost에 띄워줘"

그래프 대시보드 제작은 부담될 수 있어 선택으로 둡니다. 핵심은 ②~④(설치·질의·아이디에이션)이며, 그래프는 마지막 보너스입니다.

단계무엇이 강의 어디서

2왜 온톨로지인가 | 스킬 공유 그 이상

"②팀 표준화에 왜 굳이 온톨로지냐, 스킬만 공유하면 안 되냐"는 자연스러운 질문입니다. 답은 스킬과 온톨로지가 채우는 칸이 다르다는 데 있습니다.

스킬 = 절차 ("어떻게 행동")
"이럴 때 이렇게 처리해라"
 한 가지 작업의 실행 방법
온톨로지 = 의미 ("무엇이 어떻게 연결")
"이 도메인은 이런 개념·관계로 이뤄짐"
 팀 전체가 참조하는 공통 의미 기반

스킬만 공유하면 팀이 커질수록 각 AI가 같은 도메인을 제각각 이해합니다 ("결제" = "Payment" = "거래"가 따로 논다). 온톨로지가 채우는 세 칸:

온톨로지가 하는 일스킬로는 안 되는 이유
① 팀 공통 의미 기반모든 스킬·MCP·에이전트가 같은 entity·관계를 참조
② 영향 분석 (traversal)"이거 바꾸면 어디까지?" 스킬은 절차만, 관계를 못 따라감
③ 도메인 지식 자산화데이터팩으로 축적·공유·버전 관리
오케스트레이션이 가능하려면 모든 에이전트가 같은 의미 기반을 봐야 합니다. 그게 온톨로지이고, ②팀 표준화는 "스킬 공유"의 다음 차원입니다.
